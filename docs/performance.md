# Performance measurements and budgets

Status: measured 2026-11-05 on the development host. This document is the
reference for pipeline-level CPU budgets. It is not a claim about GPU frame
timing or real-display latency; see [What was not measured](#7-what-was-not-measured).

## 1. Scope and method

The goal is an enforceable baseline for the "silky" editing experience: how long
the real production code takes to produce preview and committed pixels at
2 MP, 12 MP and 48 MP, and what memory those operations imply.

The committed harness is `native/tests/bench_pipeline.cpp`, built by
`native/cmake/NekoPicBench.cmake` as the `bench_pipeline` executable. It calls
the production implementations directly:

- `NekoPic::Adjustments::apply` (`src/core/adjustments.cpp`)
- the filter-preview batch equivalent used by `FilterPreviews`: smooth
  downscale to 192x144, then six presets (`src/app/filterpreviews.cpp`)
- `NekoPic::Mosaic::pixelateRect` / `pixelateStroke` (`src/core/mosaic.cpp`)
- `NekoPic::Render::PreviewMath::applyRgba8` / `applyRgba64`
  (`src/render/previewmath.cpp`), the CPU mirror of the GPU shader
- `NekoPic::ImageIO::load` (`src/io/imageio.cpp`) for `assets/demo.jpg`

Method details:

- Synthetic sources are deterministic (seeded gradient + noise) and generated
  in-process. Only the demo decode reads from disk.
- Each case runs one warmup plus five measured runs. Min, median, p95 and max
  are reported; p95 uses linear interpolation between sorted samples, so with
  five samples it is close to the maximum.
- Timing is wall clock (`QElapsedTimer`). Each individual case is a
  single-threaded loop.
- Independent adjustment cases are dispatched to the Qt thread pool (up to
  eight at once by default) to keep the full 48 MP sweep near two minutes. The
  committed full dataset (`native/bench/full-parallel.md`) therefore contains
  upper bounds under all-core load. A serial `--jobs 1` reference was started
  but not completed within this spike; the flag remains available for isolated
  latency work on an idle host.
- Each case has a 1 GiB estimated-allocation guard. A case whose source plus
  result would exceed the cap is reported as skipped with a reason instead of
  being attempted. No case was skipped in the runs below.
- Memory numbers are an accounting model over `QImage::sizeInBytes`, not
  process RSS. Undo capacity uses the production 256 MiB
  `HistoryStore::DefaultBudgetBytes`.

Reproduce:

```sh
scripts/bench.sh --quick
scripts/bench.sh --quick --check --csv native/bench/quick-results.csv \
    --json native/bench/quick-results.json
scripts/bench.sh                              # full sweep, about two minutes
scripts/bench.sh --no-build --jobs 1          # serial isolated-latency reference
```

`scripts/bench.sh` configures a Release build in `native/build-bench` (ignored
by version control), builds only `bench_pipeline`, and forwards extra
arguments. To drive CMake directly, configure `native` with
`-DCMAKE_BUILD_TYPE=Release`, build the `bench_pipeline` target and run it
with the same flags. The benchmark is not registered with CTest;
`native/cmake/NekoPicBench.cmake` contains the commented out smoke-test
registration if a deployment wants one.

## 3. Measured results

Two datasets are committed:

- `native/bench/full-parallel.md` — default mode, 2/12/48 MP, adjustment cases
  up to eight at once. This is the primary full-size dataset.
- `native/bench/quick.md`, with `quick-results.csv` and `quick-results.json` —
  `--quick` (0.5/2/8 MP), regenerated by the final harness build. Its
  `--check` results are in 3.9.

Only the adjustment matrix runs cases concurrently; every other suite runs one
case at a time. The full-size adjustment rows are therefore upper bounds under
all-core load. Quick and full numbers at the same size differ by roughly
20-40% because they are separate runs on a shared host, not because the code
changed.

## 4. Budgets

Status legend:

- **Enforced**: checked by code or by the harness on every applicable run.
- **Aspirational**: a product target for the reference hardware. It is measured
  and reported, but not a CI gate; the current CPU path may fail it.

| Budget | Target | Status | Rationale / current measurement |
| --- | --- | --- | --- |
| Interactive GPU preview frame (slider drag) | <= 16 ms (60 Hz), <= 33 ms (30 Hz) | Aspirational | ADR-0003 makes the GPU the interactive path. This harness times the CPU mirror, not the shader, so the frame budget itself is not verified here. |
| Display-scale CPU preview first result (2 MP source, 1600x1000 proxy) | <= 33 ms | Aspirational | A 30 Hz fallback frame. The measured 2 MP preview is far above this; see 3.4. |
| Full-size CPU commit (2 MP) | <= 100 ms | Aspirational | Release-the-slider commit must feel immediate. 2 MP is roughly 0.19-0.26 s for exposure/contrast, so the current path misses this. |
| Filter thumbnail batch (2 MP source, six 192x144 presets) | <= 16 ms | Aspirational | One frame for the whole swatch row. Measured 16-20 ms at 2 MP. |
| Warm import of a 1800x1200 JPEG | <= 100 ms | Aspirational | Decode plus the existing limit checks. Measured about 46 ms warm, so it passes; cold disk is not measured. |
| Mosaic on 12 MP, ~9% ROI | <= 100 ms | Aspirational | Interactive mosaic should land within a few frames. RGBA8 is roughly 64-180 ms depending on rectangle versus stroke and block size. |
| History budget | 256 MiB unique image storage | Enforced | Defined by `HistoryStore::DefaultBudgetBytes`; old entries are trimmed. At 12 MP only 1-2 snapshots fit, and at 48 MP none fit (see 3.6). |
| Harness allocation guard | 1 GiB estimated peak per case | Enforced | Guards the benchmark itself; oversized cases are skipped with a reason. |
| Regression ceilings (`--check`) | 2 MP filter batch p95 <= 60 ms; first preview p95 <= 500 ms; exposure +1 p95 <= 800 ms; decode p95 <= 150 ms | Enforced when `--check` is passed | Deliberately loose regression guards for a shared host. Product targets above are tighter and remain aspirational. |
| Benchmark in CTest | not registered | Policy | The full run is slow and host-dependent. A quick smoke test can be registered manually; the CMake fragment documents the one-liner. |

Notes on policy:

- The 16/33 ms targets are product targets, not current achievements. The CPU
  path is currently 5-10x above them at screen resolution; that is the reason
  ADR-0003 keeps the GPU path for interaction and the CPU path authoritative
  only for commit/export.
- The 48 MP commit and undo story needs a product decision: the existing
  256 MiB history budget cannot retain one rendered snapshot at that size.
  Either the budget grows for large images, or the UI must communicate that
  undo beyond the first edit is unavailable.

## 5. Known bottlenecks

1. **Adjustment math is scalar and per-pixel.** The integer path converts the
   source to `Format_RGBA64`, then evaluates three `double` tone curves,
   luminance and three `std::lround` calls per pixel. This is the dominant cost
   at every size. The filter path adds a second full pass when intensity is
   non-zero. Measured cost is roughly 90-165 ns per pixel across sizes on
   this host (parallel-run upper bounds).
2. **The filter preview batch downscales the full source on every batch.** The
   six 192x144 applications are cheap; the `QImage::scaled(..., Smooth)` of the
   12 MP or 48 MP source dominates. Batch time therefore grows with source
   resolution even though the output is capped at 192x144.
3. **Mosaic RGBA8 uses `QImage::pixelColor` / `setPixelColor`.** That path
   constructs `QColor` objects per pixel and is about 1.8-2x slower than the
   direct `QRgba64` path. Block size 128 is also slower than 8/32 because every
   block reads the full grid-aligned block, including pixels outside the
   selected ROI.
4. **Undo history is effectively unavailable for large images.** At 12 MP an
   8-bit base is 45.8 MB and each rendered snapshot is 91.6 MB, leaving room
   for one or two entries; at 48 MP the base plus one render already exceeds
   256 MiB.
5. **The CPU mirror is substantially faster than the authoritative path**
   (roughly 3x at 2 MP). That supports the GPU-preview design, but it also
   means the authoritative commit is the tail users feel when they release the
   slider.
6. **Queue overhead is not the problem.** The QtConcurrent round trip at the
   tested size is within the same order as an inline render; the render itself
   dominates.

## 6. Next measurements

- GPU frame timing with real RHI timer queries on the actual backends, plus
  input-to-photon latency on Wayland and X11.
- Process RSS peak and allocation churn for a 48 MP document with a real edit
  and undo sequence (the current numbers are image accounting, not RSS).
- Cold-cache import (drop caches or a fresh file) and large-format decode
  (PNG16, TIFF, WebP) against the `ImageIO::Limits` path.
- Save/export timing for PNG and JPEG at 2/12/48 MP, including the
  transparent-to-white JPEG composition.
- A CPU adjustment prototype with SIMD/parallel row processing to estimate the
  best achievable commit latency before committing to more GPU work.
- Mosaic at the 4096-point / 4096 px-diameter limits, and stroke shapes that
  maximize ROI overlap.
- The `--check` ceilings on a reference machine (they are intentionally loose
  on this shared host).

## 7. What was not measured

- GPU shader execution time, GPU memory, or differences between OpenGL, Vulkan
  and other RHI backends. Only the CPU mirror of the shader formula was timed.
- Real-display latency, compositor behavior, Wayland versus X11, high-DPI
  scaling, or pen/touch input.
- Peak process memory or GPU texture memory for a 48 MP document. The memory
  section is a `QImage::sizeInBytes` model with the 256 MiB history budget; it
  is not RSS.
- Save/export timing, cold-disk import, network filesystems, or removable
  media.
- Multi-instance behavior, long-session thermal throttling, and background
  task scheduling under a full editor session.
- Correctness of the GPU preview. The existing `previewmath` tests cover
  CPU/CPU parity; this harness only times the mirror.

## 8. 2026-11-05 adjustment-path optimization

The authoritative CPU adjustment path was optimized after the baseline above:

- per-apply 16-bit tone transfer table instead of per-pixel `exp2`/division;
- tone-only path skips luminance/saturation (with a rounding-boundary guard);
- filter pass fused into the first scan; preset parsed once; warm/vintage/cool use channel LUTs;
- `std::lround` replaced by exact non-negative rounding;
- row-parallel processing (`src/core/rowparallel.h`): ≥1 MP, up to 8 workers, serial fallback for small/narrow/single-core inputs.

Exactness: a verbatim legacy reference implementation is compared byte-for-byte in `tests/tst_adjustments.cpp` across 1x1, 1xN, Nx1, 64x64, 1024x768, 2048x1536, RGBA8888/RGBA64/float formats, 26 parameter sets, all 16-bit channel values, alpha edges and P3/DPI metadata. 45 test functions pass; ASan+UBSan pass (TSAN was not run).

Focused `Adjustments::apply`, Release, shared host, median of 5:

| Size | Case | Before ms | After ms | Speedup |
| --- | --- | ---: | ---: | ---: |
| 2 MP | exposure +1 | 208.8 | 7.9 | 26.4x |
| 2 MP | combined vintage | 322.4 | 16.0 | 20.2x |
| 12 MP | exposure +1 | 1137.0 | 28.8 | 39.4x |
| 12 MP | exposure +2 contrast | 1241.6 | 76.1 | 16.3x |
| 12 MP | saturation -1 | 1297.2 | 65.0 | 20.0x |
| 12 MP | mono | 908.4 | 89.3 | 10.2x |
| 12 MP | combined vintage | 1931.6 | 82.6 | 23.4x |

Remaining bottlenecks: `QImage::convertToFormat(RGBA64)` is now a significant serial share of RGBA8888 tone-only cases; mono/vivid still need cross-channel math; tables are rebuilt per call (negligible at large sizes). Integrated `bench_pipeline --quick` cases run concurrently and therefore show different (higher) medians than the focused table.
